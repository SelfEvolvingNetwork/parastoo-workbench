# کارگاه پرستو (Parastoo Workbench) — سندباکس دائمی عامل روی سرور مالک

> مخاطب: مالک/نصاب کارگاه + کلاه عامل کارگاه (I4) · نقش‌ها: `docs/ROLES.fa.md` مخزن پرستو

> **قرار مالک (۲۰۲۶-۱۱-۱۰):** «بخشی را در سرور من به‌عنوان سندباکس درست کن و آزمایش‌های خودت را همیشه آنجا انجام بده» و «سعی کن تا می‌توانی ابزارهای موردنیازت را روی سرور من نصب کن… به سندباکس روی سرور من به‌عنوان یک روش اصولی و راهبردی و پایدار نگاه کن؛ این فرایند بلندمدت است.»

> **نقشهٔ جامع مستندات خانوادهٔ پرستو (۴ مخزن):** `docs/INDEX.fa.md` در مخزن `parastoo` — تنها درگاه ورود به مستندات (ترتیب خواندن شروع سرد + «موضوع → سند مرجع»).

این مخزن، **نسخهٔ رسمی و بازتولیدپذیر** همان سندباکس است: جای ثابت اسکریپت‌ها، نصب‌کنندهٔ خودکار، دروازهٔ سبز سرور، کلاینت عامل و قرارداد مکتوب. اگر سرور بازسازی شود، کل کارگاه با **یک فرمان** برمی‌گردد.

## ایده در یک خط

آزمایش سنگین همیشه روی سرور مالک انجام می‌شود (جایی که داکر و ایمیج واقعی پرستو هست)، نه در سندباکس محلیِ زودگذر عامل — و همهٔ ابزارِ این کار، نسخه‌دار و روی گیت‌هاب است.

## چیدمان مخزن

| مسیر | نقش |
| --- | --- |
| `server/bootstrap.sh` | نصب/ارتقای کارگاه روی سرور — idempotent؛ از داخل کلونِ مخزن روی سرور اجرا می‌شود |
| `server/gate.sh` | **دروازهٔ سبز روی سرور**: ruff + `bash -n` + چهار سوئیت اسموک داخل ایمیج `parastoo/core:latest` (آفلاین، بدون شبکه) |
| `server/cleanup.sh` | پاک‌سازی دوره‌ای: `tmp/` قدیمی‌تر از ۷ روز، worktreeهای مرده، ایمیج‌های آویزان |
| `server/selfcheck.py` | خودآزمایی کارگاه — خروجی JSON (`--human` برای گزارش خوانا) |
| `server/SANDBOX_README.fa.md` | READMEیی که روی سرور در `/opt/parastoo-sandbox/README.fa.md` نصب می‌شود |
| `client/wb.sh` | کلاینت محلی عامل: `exec` / `sync` / `fetch` / `gate` / `deploy` / `verify` / `doctor` / `status` / `update` — همه از راه پل access-agent |
| `docs/WORKBENCH.fa.md` | قرارداد کامل: چرخهٔ «اول سندباکس سرور»، مرزهای امنیتی، عیب‌یابی |

## نصب روی سرور (یک فرمان، از راه پل)

```bash
# از ماشین عامل — پل access-agent لازم است:
bash /home/z/my-project/scripts/server_exec.sh \
  'SB=/opt/parastoo-sandbox; if [ -d $SB/workbench/.git ]; then git -C $SB/workbench pull --ff-only; else git clone --depth 1 https://github.com/SelfEvolvingNetwork/parastoo-workbench $SB/workbench; fi && bash $SB/workbench/server/bootstrap.sh'
```

نصب‌کننده خودش این‌ها را می‌کند: ساخت `tmp/ results/ logs/ tools/bin` · همگام‌سازی اسکریپت‌ها از مخزن · **نصب ruff از ریلیز گیت‌هاب** (سرور به گیت‌هاب دسترسی دارد؛ pip ندارد) · کلون مخزن پرستو برای دروازه · خودآزمایی پایانی.

## استفادهٔ روزمره (کلاینت محلی)

```bash
bash client/wb.sh doctor          # سلامت کارگاه + انبارگردانی ابزارها
bash client/wb.sh gate <sha>      # دروازهٔ سبز کامل روی سرور، روی درخت کاریِ همان کامیت
bash client/wb.sh publish         # سیفِ انتشار: باندل → سرور → پوش به گیت‌هاب از سرور
bash client/wb.sh deploy          # استقرار صریح: POST /api/admin/parastoo/update از راه پل
bash client/wb.sh verify <sha>    # پول /api/version تا کامیت مستقر شود + e2e_live
bash client/wb.sh sync فایل /opt/parastoo-sandbox/tmp/x  # آپلود فایل (base64 chunked)
```

## استقلال از سندباکس محلی — سیفِ انتشار (publish airlock)

سندباکس محلی عامل شکننده است و ممکن است **وسط کار** بمیرد (مُهر ۱۴۰۵ دوبار اتفاق افتاد). راهبرد: بعد از کامیت، هرچه زودتر کار به سرور برود؛ پوش دیگر به سلامت محلی وابسته نیست:

```
کامیت محلی → wb publish:
  ۱) باندلِ گیت (origin/main..HEAD، معمولاً چند KB) ساخته می‌شود
  ۲) باندل با sync آپلود می‌شود (chunked + sha256) — اگر محلی همین‌جا بمیرد، کد روی سرور سالم است
  ۳) توکن لحظه‌ای از broker گرفته می‌شود (کوتاه‌عمر، فقط در حافظه)
  ۴) سرور: bundle unbundle + git push به گیت‌هاب
  ۵) راستی‌آزمایی ls-remote == HEAD + پاک‌سازی فوری اعتبار و باندل
```

**بهداشت راز:** توکن هرگز روی دیسک سرور یا لاگ نمی‌نشیند — فقط چند ثانیه در `/tmp` با chmod 600 و بلافاصله حذف؛ در کانال پل (TLS پین‌شده) به‌صورت base64 می‌رود؛ توکن دائمی گیت‌هاب هرگز وارد سرور نمی‌شود.

با این، چرخهٔ کامل «کد → گیت‌هاب → دروازهٔ سرور → استقرار» فقط با یک اتصالِ پل کار می‌کند و سندباکس محلی فقط برای ویرایش و کامیت لازم است.

## قواعد طلایی کارگاه (غیرقابل مذاکره)

1. **بیرون از درخت نصب:** `/opt/parastoo` (نصب تولیدی) هرگز از کارگاه دست نمی‌خورد — آپدیت و استقرار اینجا را پاک نمی‌کنند.
2. **بدون راز:** هیچ توکن/رمز/.envی در کارگاه روی سرور نوشته نمی‌شود؛ احراز فقط در لایهٔ پل است.
3. **دروازهٔ دومرحله‌ای:** پوش به `main` پرستو فقط پس از دروازهٔ سبز محلی؛ **استقرار** فقط پس از دروازهٔ سبز سرور (§۳ قرارداد).
4. **منابع:** سرور ۴GB رم دارد — کار سنگین هم‌زمان با استقرار ممنوع؛ `tmp/` خودپاک (۷ روز)؛ بدون بیلد داکر اضافه.
5. **شفافیت:** هر نتیجهٔ دروازه در `results/gate-history.log` سرور ثبت می‌شود؛ عامل حق پاک‌کردنش را ندارد.

## درس‌های ثابت‌شدهٔ محیط سرور (۱۴۰۵/۰۸)

- **DNS خروجی بسته است به‌جز گیت‌هاب** (github.com، api.github.com، raw، codeload، objects همه باز؛ pypi/npm بسته). نتیجه: ابزارهای تکی‌فایلی از ریلیز گیت‌هاب نصب می‌شوند، نه pip.
- **سوئیت‌های اسموک داخل ایمیج `parastoo/core:latest`** اجرا می‌شوند (وابستگی‌های پین‌شده از قبل در ایمیج است) با mount درخت کاری و `--network none` — بدون هیچ نصب تازه.
- پل exec هر فرمان را **۶۰ ثانیه** می‌کشد؛ کارِ طولانی با `nohup … &` detached + پولینگ (`wb gate` همین‌کار را می‌کند).
- در `pkill` الگوی خود-تطبیقی به‌کار ببر (`pkill -f 'pat[t]'`).
